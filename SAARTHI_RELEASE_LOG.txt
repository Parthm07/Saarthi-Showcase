CLOUD SCHEMA PREFLIGHT

1. Compare the live Railway web service's CLOUD_DB_URL with the Neon project,
   branch, and database you are inspecting. Keep the connection URL private.
   The current business database is saarthi_live. The same name can exist on
   multiple branches.
2. In Neon SQL Editor, select that branch and database. Paste the entire
   verify_cloud_schema.sql file and click Run. It reads catalogue metadata only.
3. Check database_name. OK means the expected schema matches. MISSING names a
   missing object. MISMATCH shows the expected and actual definitions. Review
   the definition against the migration before applying any change. Equivalent
   definitions with different names or PostgreSQL output can also be flagged.
4. Before a release that depends on a schema change, apply the specific
   migration to the live database and rerun the audit. Deploy after confirming
   the new dependencies are in place. Verify the affected workflow separately
   from the schema, using a test environment for order creation and Tally sync.

After changing PostgreSQL schema definitions, regenerate the SQL from a clean
local PostgreSQL reference. Apply cloud_db.create_schema() to a disposable
local database named postgres with user saarthi_audit. Set
SAARTHI_SCHEMA_REFERENCE_PORT to its loopback port and run
python generate_cloud_schema_audit.py. Commit the updated SQL with the change.
